# Why aqua-registry-g2

aqua-registry-g2 is the second generation of
[aqua-registry](https://github.com/aquaproj/aqua-registry). This is what the first one
couldn't do well, and what this one does about each. The overview it started from is
[aquaproj/aqua#5286](https://github.com/aquaproj/aqua/issues/5286), which also covers the
lock file on aqua's side.

## The problems

Some of these could have been solved by improving aqua-registry. Taken together they come
from one thing: a definition in aqua-registry is written by hand and describes every version
at once, so whatever a release does that the definition didn't foresee is somebody's work
before anyone can install it.

- Maintaining aqua-registry takes a lot of work.
  - An upstream that renames its assets is a definition somebody has to fix by hand.
  - A new os/arch, or a release that starts carrying a cosign signature or a GitHub
    artifact attestation, isn't noticed by anything.
  - Fields such as `files` can't be generated.
- Whoever installs pays for it. A release that renames its assets can't be installed until
  the definition is fixed, and then not until they update the registry they use.
- Checksum verification is off by default, so most installs verify nothing.

## What g2 does about them

A `registry.json` is generated for every version of a package, in CI, from that release's
actual assets. What a version resolves to -- the asset name, the format, the files inside
the archive, the checksum -- is decided once, when it is generated, rather than every time
somebody installs it.

- An upstream renaming its assets needs nobody. The asset names aren't read from the
  definition: they are inferred from the release's own asset list, so the next version is
  generated under whatever it is called now.
- A new os/arch is found the same way, since it is one more asset in the list.
- `files` is checked against the archive rather than trusted. CI downloads every asset a
  generated file describes, on a machine of the environment each entry is for, opens it and
  confirms the files are where the entry says.
- Every entry carries the digest of the asset itself, so aqua verifies the checksum without
  anyone turning anything on.
- Signatures are verified here, once, rather than on every install. The signature bundle
  beside an asset is opened, and the entry names the workflow that signed it and the
  issuer that vouched for it. A version that carries less than the one before it -- a
  signature that stopped being published -- waits for a person, because that is also what
  an attacker's release would look like. Verifying at install time stays available to
  whoever wants it.
- Nobody waits for a definition to be fixed or for the registry to be updated. Versions are
  generated by a chain of runs that is always going, and most pull requests merge
  themselves once the checks pass.

A `registry.json` holds one version and no `version_overrides`, `overrides` or templates, so
a tool reads it as it is. It is written once, and replaced only when the definition it came
from turns out to be wrong: generated again from the fixed definition and reviewed by a
person, never edited by hand.

The definition, `registry.yaml` in each package's directory, is still there. It holds what a
release can't be read for -- a filter narrowing which assets are the command, the path of a
file inside an archive, aliases -- and it is the one file a person writes.

## What it costs

- A version can't be installed until its `registry.json` has been generated. The runs are
  chained rather than scheduled so that the lag stays short, but it isn't zero.
- Mutable versions such as `latest` and `nightly` are never generated, since a file written
  once can't describe something that changes.
- The inference can choose the wrong asset when a release carries more than one program.
  The check usually catches it, because the archive doesn't hold the command; an asset that
  is the wrong build of the right program would pass. `all_assets_filter` and
  `asset_filters` in the definition are how that is fixed, and they are written by hand.

## What happens to aqua-registry

aqua-registry is expected to move here, stop accepting pull requests and be archived.
Until then, a package it gains reaches this registry on its own: a run adds whatever
aqua-registry has gained since the last one.
